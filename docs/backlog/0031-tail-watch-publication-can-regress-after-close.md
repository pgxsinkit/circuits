# 0031 — Tail watch publication can regress after close

Status: resolved (fixed 2026-10-03; consumer reproduction and qualification retained)
Opened: 2026-10-03 · Area: `apps/durable-streams/src/handlers.rs` tail publication, long-poll and inline SSE
Reopen trigger: a delayed callback again regresses cache/watch bytes or closure, an inline/reactor reader misses committed bytes or EOF, or a valid initially closed PUT body cannot advance its retained closed notification.

Urgency before fix: medium delivery/liveness defect reproduced locally on inline SSE and waiting long-poll. No production incident is known. The native engine uses long-poll, whose timeout rechecks shared state. Linux reactor SSE reads shared state directly and does not use the regressing watch payload. [0030](0030-checkpoint-tail-can-cross-a-rejected-append.md) is now fixed independently.

## Source evidence and boundary

Independent review of [0029](0029-general-metadata-writers-capture-speculative-append-state.md) found a preexisting publication gap. `publish_durable_tail` advances `Shared.durable_tail` monotonically and captures `closed_durable` under the shared write lock, then releases it before updating the resident cache and calling `tail_tx.send_replace`. An earlier callback can pause after advancing the shared frontier. A later callback can publish a greater frontier, followed by a successful close. When the earlier callback resumes, it can replace the watch value with its lower byte count and `closed=false`; the monotonic shared check happened before that newer publication.

Waiting long-poll reads the watch payload directly, so it can lose prompt delivery/EOF notification, but its deadline path rechecks `st.tail()`. A newly opened long-poll checks shared state before subscribing and returns a known close immediately. Inline `SseSource::next` uses its watch payload for bytes and closure; shared reads only help its up-to-date/initial-control checks. Its idle heartbeat reports open and its total deadline ends without a shared close recheck. `handle_sse` initializes this receiver from the watch even when its initial shared tail is closed. A new inline SSE consumer after the stale replacement could therefore miss the later bytes/close until reconnect. Forked or tiered streams use this inline path; the Linux reactor reads shared `durable_tail`/`closed_durable` directly. Resident-cache replacement can also regress, with fallback reads providing bytes on a miss.

This pattern predates the dedicated close worker. Committed metadata capture does not qualify ordering of the separate watch/cache publication. This was originally a source-review lead; the execution below subsequently confirmed consumer failure.

## Original reproduction and acceptance plan

Add a test-only hook immediately after the real shared frontier advancement and before cache/watch publication. Hold append A there, complete a later append B and close, then release A. Compare watch and shared state; directly drive inline `EventSource` chunks or use a real fork/tier stream to disable the reactor. Check delivery of B's bytes and terminal control, a waiting long-poll's prompt completion, and a new subscriber after closure. Always release hooks and join writers before assertions/teardown. Demonstrate the failed consumer behavior before implementation.

Consider serializing the frontier/cache/notification publication or deriving consumer decisions from authoritative shared state while keeping watch as a wake mechanism. These are options, not an established design. Preserve monotonic bytes/closure, cache-before-wake, chunk boundaries, close durability, delete identity notification, cancellation and cross-stream progress. Qualify reordered callbacks, concurrent close, inline/reactor SSE and long-poll, then run both validation gates.

## Executed reproduction and selected boundary

`bun run test:durable-streams e2e_tail_publication_reordering -- --nocapture` exited 101 twice on the actual consumer assertion, in 1.07 and 1.39 seconds. No compile or setup corrections preceded those semantic failures. A real empty parent and fork child select the actual inline SSE fallback on Linux; the test asserts the handler's `EventSource` has no reactor registration. No shared tail or watch value is fabricated.

Append A lands six bytes (`first|`) and pauses immediately after monotonic shared-frontier promotion, before cache/watch publication. A real long-poll is pinned and polled once into `Pending` at `offset=now`, capturing position six. It remains unpolled while append B lands seven more bytes (`second|`) and close succeeds. Both publish a thirteen-byte closed watch before A resumes. Releasing and joining A then leaves authoritative shared state at `Tail { bytes: 13, closed: true }`, while its stale callback replaces the watch with `Tail { bytes: 6, closed: false }`.

A fresh actual inline SSE reader consequently emits only `data:first|`, advertises offset six, omits terminal `streamClosed`, and stalls on its next chunk. The waiting long-poll also fails to complete within the short prompt-delivery check. All writes and close returned 204. A full reboot retains exact `first|second|` bytes and thirteen-byte durable EOF before the final assertion. This is a live notification defect: storage/recovery remain sound, and long-poll's ordinary deadline recheck can recover delivery. The fixture does not establish permanent native-engine data loss or a socket-level SSE disconnect failure.

Root showed three ranked falsifiable explanations before selecting implementation: out-of-order publisher notification, consumers trusting stale watch values, and resident-cache replacement. The actual shared/watch split and intact recovery identify the publisher ordering gap; a consumer-only change would leave regressing notifications/cache visible. Independent review selected the existing watch channel write lock (`send_if_modified`) as the runtime cache/notification boundary. Accepted append publication installs its resident chunk before replacing the watch; stale/equal appends and open-after-close candidates cannot replace the newer notification or cache. Close shares that boundary, preserves the cache, keeps byte count monotonic and makes closure sticky. Reactor wake follows lock release.

The shared-state promotion remains monotonic and releases its guard before notification. This avoids another per-stream lock/allocation and avoids nesting Shared with the watch/cache publication locks. Existing consumers copy/drop watch borrows before touching shared state or cache; cache slices release their guard before returning. Startup recovery's unconditional watch publication is exclusive and may legitimately lower a torn tail, so it is outside runtime filtering. TTL expiry and direct DELETE use the separate sticky deletion watch; direct-DELETE SSE semantics remain [0021](0021-direct-delete-sse-terminal-notification.md).

## Implemented resolution and qualification

`StreamState::publish_tail` owns the runtime notification/cache boundary for ordinary and initial PUT append completion and the dedicated durable close worker. It uses `send_if_modified` even with no watch receivers. Accepted append candidates install their owned `Bytes` chunk and update `Tail` under that lock; stale/equal bytes and an open candidate following a close no-op. Close preserves the cache, maxes the byte frontier and makes closure sticky. A nonempty initially closed PUT can still advance an already closed watch with a higher closed candidate. Debug assertions describe the internal chunk-end and EOF-candidate contracts; runtime ordering does not depend on those assertions. Reactor wake happens only for changed publication and after releasing the publication locks. Existing operation ownership still spans publication, so cancellation and direct DELETE retain their admission boundaries.

The original consumer-red fixture passed with its scheduling unchanged. Four new public-path tests now cover:

- Delayed A after B plus close: waiting long-poll and fresh fork-inline SSE receive all remaining bytes and EOF; watch agrees with authoritative state, B's resident chunk survives, and full reboot preserves exact bytes/closure.
- Close before delayed A notification: existing inline SSE and a new `offset=now` subscriber both observe EOF and terminate; another stream acknowledges while A is paused.
- Both memory and WAL modes: a nonempty initially closed fork PUT retains its complete body, cache and EOF with zero receivers; a real woken long-poll uses the installed cache and close preserves it. Full reopen checks exact bytes and closure. Memory-mode process reopen is not power-loss durability.
- Linux reactor: a real TCP pair receives the registered root-stream SSE body, data and terminal control, completes the chunked body and releases its subscriber permit with zero watch receivers. The fixture waits for the initial control before appending to exercise wake-driven delivery and leaves the global reactor running.
