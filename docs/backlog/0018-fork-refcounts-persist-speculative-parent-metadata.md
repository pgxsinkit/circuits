# 0018 — Fork reference updates can persist speculative parent append metadata

Status: dropped (fixed and qualified 2026-10-03)
Opened: 2026-10-02 · Area: `apps/durable-streams/src/store.rs` (`create`, parent release, `Meta::capture`, `write_meta_sync`), `handlers.rs` append publication
Reopen trigger: a regression shows a reference-only write changing other metadata, an uncertain write releasing a required parent pin, or owned release retry losing its work. General writers and graph recovery have separate entries 0029 and 0019.

Urgency: resolved for the reference-write route. The reproduced failure affected DS fork users; the ordinary engine path does not use forks.

## Evidence and priority

Fork reservation/release changes `ref_count` and writes the parent's general metadata snapshot. Append handling can change speculative close, producer/dedupe or writer state before WAL staging/acknowledgement; `Meta::capture` can therefore persist that state as a side effect of a reference-only update. This is a durability concern for fork users. The ordinary Circuits engine does not use the DS fork API.

On 2026-10-03, `bun run test:durable-streams persist_an_inflight_append_snapshot -- --nocapture` ran two real-handler regressions in `wal/e2e_tests.rs`, both red in 0.03 seconds after compilation. A stage hook paused a 512-byte producer append against a 256-byte WAL segment, after its close/producer/writer-sequence mutations and before staging. Real fork PUT or child DELETE persisted the parent reference update while paused. Releasing the hook produced POST 500, live metadata rollback and an empty data file, then the harness crashed and fully reopened. The captured sidecar, recovered sidecar and reopened live state all contained the failed append's `closed=true`, `closed_by=[failed-producer,1,0]`, producer epoch 1/sequence 0, and `last_seq_header=0001`, with `durable_tail=0`. The expected image was open with no producer or writer-sequence state. This is an executed semantic failure, not a compilation failure or source inference.

Second batch prepares new streams privately and checks failed-create compensation. First-batch metadata/delete exclusion and queued soft-parent cleanup revalidation do not make parent reference writes field-specific. Fork graph recovery is separately [0019](0019-fork-graph-and-reference-recovery.md). General metadata sweeps/checkpoints/tier writers are a distinct source-confirmed candidate, [0029](0029-general-metadata-writers-capture-speculative-append-state.md), not qualified by narrowing fork reference writes.

Source: [5093702ce3a55007fe201b3615f12d6f65007410](https://github.com/indexedlabs/durable-streams-rust/commit/5093702ce3a55007fe201b3615f12d6f65007410). Useful upstream tests: `fork_reservation_does_not_persist_an_inflight_append_snapshot`, `parent_refcount_release_does_not_persist_an_inflight_append_snapshot`, `parent_refcount_release_rolls_back_when_the_narrow_merge_fails`.

## Proposed boundary and acceptance

Merge only the reference field into previously committed metadata while holding `meta_lock`, checking the exact incarnation and preserving allowed soft-parent updates. Failure must restore or conservatively retain the pin; do not persist a speculative close/dedupe snapshot or permit deletion of a still-needed parent. Pause append before staging and before durable publication, cross reservation/release, inspect the disk image, then crash/reopen and assert committed bytes and producer state. Include narrow-merge/fsync failure and delete/rollback races. Extract the fix without upstream subscription/reaper architecture, and run both repository gates.

## Implemented boundary and qualification

The narrow writer reads the existing parent sidecar while holding `meta_lock`, validates its id/path/base offset and immutable configuration, and replaces only `ref_count`. Missing, malformed or foreign sidecars, invalid deadlines and durable counts exceeding live pins fail without a general-capture fallback. A lower disk count remains valid after an uncertain release rename. Reservation count changes occur inside that serialization boundary, while the existing parent operation admission makes DELETE wait. Count arithmetic is checked.

A reservation owns its increment before attempting the write, including when rename succeeds but directory fsync fails. Failed-create compensation first removes and directory-syncs the child artifacts, then attempts the narrow parent release. It lowers the in-memory count only after durable success. Incomplete compensation retains a conservative live pin and reports the blocked child path.

After durable child removal, one owned task retains the parent and child's identity while releasing the reference. It releases the removed child's state and file handle rather than holding its unlinked data allocation throughout a storage outage. Each attempt locks parent retirement then metadata, checks the registered incarnation, and writes an absolute target derived from the retained live count. A failed attempt keeps that count and retries asynchronously, with 100 ms to 5 second backoff; a post-rename failure cannot cause the next attempt to decrement twice. A concurrent new reservation composes with the retry. Successful release may schedule zero-reference soft-parent cleanup, which still revalidates behind its barriers and releases ancestors only after physical removal. The noneligible cleanup branch no longer captures general append metadata.

The two original regressions passed after this change. Added cases compare every known metadata field except the changed reference count, refuse missing/corrupt/foreign proof, exercise count limits, fail reservation and release both before replacement and after rename, retain pins during failed compensation, retry around a fresh reservation and repeated child DELETE, and defer nested soft-parent cleanup until repair. The before-publication fixtures stop committers after an acknowledged prefix, prove a new append is staged and waiting for durability, cross both real fork-reference paths, then complete the append and reopen. A surviving child retains its inherited prefix.

Failure injection after rename happens after the real temporary-file sync and rename, immediately before directory fsync; it is not a real filesystem power-loss experiment. The staged fixture completes the WAL barrier before restart and makes no claim about unsynced WAL survival. Process-owned retry ends at process shutdown; graph reconstruction after child unlink remains 0019. General sweeps/checkpoints/tier capture remain 0029. No subscriptions/reaper architecture or dependency changes were introduced.

The bounded implementer changed `store.rs` and `wal/e2e_tests.rs`; coordinator inspection and independent read-only review accepted the final diff. Review identified unnecessary retention of the removed child's state/file descriptor during retries; the parent-only owner fixes it, and a Weak-reference regression proves the child drops while its parent pin remains until repair. Thirteen new tests were added: nine store cases and four real-handler append-window cases. Focused runs passed the original red-to-green pair, both staged-publication cases, the store/fork suites and the final 16-case parent filter.

Both `bun run validate` and `bun run validate:full` passed on the final production/test code: 425 engine Rust unit tests and its other binaries, 177 log-server unit tests, eight CLI cases, 82 TypeScript unit tests, all 246 engine integration tests across 61 files, and 332 protocol cases. The two existing Rust ignores and six protocol skips remain. Output was captured directly by the command tools without redirected files. The subsequent qualification edits change documentation only.
