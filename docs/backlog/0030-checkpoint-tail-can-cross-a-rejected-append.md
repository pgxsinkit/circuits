# 0030 — Checkpoint tail capture can cross a rejected append

Status: dropped (fixed 2026-10-03; regression and recovery qualification retained)
Opened: 2026-10-03 · Area: `apps/durable-streams/src/wal/shard.rs` checkpoint tail capture, `handlers.rs` write/stage rollback, `wal/recovery.rs` tail reconciliation
Reopen trigger: a rejected append again crosses checkpoint capture, valid retained WAL is refused by the recovery guards, or a recovered stream publishes a frontier unsupported by its available bytes. Same-length content corruption requires independent evidence and a separate repair design.

Urgency before fix: high recovery/offset corruption defect reproduced locally on ordinary POST/checkpoint paths. No production incident is known.

## Original source evidence and separation

While isolating [0029](0029-general-metadata-writers-capture-speculative-append-state.md), the implementer found that checkpoint captures `Shared.tail`, not just append metadata. `write_wire` advances that writer-facing tail before WAL staging. `stage_for_durability` registers the stream dirty before attempting `reserve_and_stage`; a stage failure then truncates the data file and restores the writer tail. Checkpoint captures the tail/file pair, performs its file barrier, then persists the tail map without excluding that write/stage/rollback window. A barrier proves the captured bytes reached storage at that moment; subsequent rollback can truncate those same bytes.

At diagnosis, recovery merged sidecar proof, checkpoint tail and replayed record ends by maximum. `reconcile_tail` truncated a longer file, but for a shorter file assumed replay had already extended it, then published the logical frontier and appender count. A falsely high checkpoint tail with no corresponding WAL record could therefore publish an offset beyond physical bytes. The original observation was source-derived; the executed result below subsequently confirmed it.

The 0029 checkpoint regression pauses after a known committed tail capture before starting the rejected append. Its exact acknowledged bytes survive reboot, establishing metadata contamination independently; it does not qualify this tail-proof path. General committed metadata views do not change checkpoint's `Shared.tail` capture.

## Original reproduction and acceptance plan

Use the same tiny-segment WAL harness and existing pre-stage hook. Commit a small baseline, pause an oversized POST after its bytes/tail mutation and dirty registration but before staging, and run the real checkpoint while paused. Inspect its persisted tail map, always release/join POST 500 and verify live rollback, then crash and fully reopen. Assert physical bytes, GET/HEAD offsets, appender position and a following successful append agree; repeat reopening. Compare the ordinary writer path with the post-tail-capture isolation fixture. Do not manufacture `Shared.tail` or the tail map to claim this race reproduced.

Do not blindly substitute `durable_tail`: WAL durability can advance before the corresponding async callback publishes that reader frontier. A checkpoint that recycles those records while recording a lagging reader tail could lose acknowledged bytes after the callback completes. Qualify a coherent accepted/staged tail boundary against the checkpoint LSN, or exclusion of synchronous tentative write/stage/rollback during capture; these are options, not an established design. Preserve registration-before-staging, durability-before-recycle, off-lock WAL waits, hard-retirement exclusion, compaction file/base consistency and progress on other streams. Test stage rejection, out-of-order publication, newly durable records, concurrent checkpoint/retirement and repeated crash recovery. Run both repository gates after implementation.

## Executed reproduction and selected boundary

`bun run test:durable-streams e2e_checkpoint_tail_does_not_certify_rejected_append -- --nocapture` exited 101 twice on the semantic assertion: checkpoint tail `Some(521)` versus acknowledged prefix 9. The fixture uses real handlers and the existing pre-stage hook, not fabricated tail/proof values. Its initial body-accessor compile mismatch and corrected wire-offset/plain-POST expectations are fixture corrections, not red evidence.

An acknowledged `baseline|` is checkpointed at nine bytes. A 512-byte body advances the tentative tail to 521 and registers dirty work before the paused stage. Checkpoint completes while paused and records 521. Releasing the hook produces POST 500 because the record cannot fit the 256-byte WAL segment; live physical bytes, writer tail, reader tail and appender position all roll back to nine. Full reboot retains physical nine but publishes writer/reader/appender 521, and GET/HEAD advertise next offset 521 (GET declares 521 body bytes). A following successful plain POST physically leaves 14 bytes but advances the logical frontier to 526. A second reboot refuses the resulting WAL hole: its record starts at 521 beyond physical length 14. The test captures all these views before its final assertion.

The evidence identifies checkpoint certifying a tentative prefix which rollback subsequently truncates, rather than recovery alone inventing an otherwise valid proof. The selected fix uses a short synchronous per-stream boundary around both initial PUT and POST data writes through staging success or full rollback. Checkpoint takes that boundary only while capturing the accepted tail and paired file handle, releasing it before barrier, proof persistence, recycle and metadata IO. It never waits on the async appender: compaction holds that lock across queued blocking work, so acquiring it from a checkpoint worker can create a one-worker-pool resource deadlock. No boundary guard may cross a WAL or blocking-pool await.

The floor remains captured before dirty-epoch drain. Every staged LSN at or below that floor registered its stream before it became durable; capture sees either its accepted prefix or completed rollback. Later failed writers truncate only to a pre-write position at or beyond that captured prefix. A separate accepted-tail field updated after staging would leave a publication window in which the WAL floor already covers bytes absent from the field. Existing compaction captures/swaps file/base atomically and fsyncs its residual before replacement; it does not need a new guard across its awaits. The boundary adds one synchronous lock acquisition per body and can delay checkpoint behind synchronous WAL rotation; no throughput impact has been measured.

## Existing corruption and recovery qualification

The original regression also exposed recovery of already false proof. Preventing new bad captures does not make those existing files sound. After replay, a physical live suffix shorter than `logical_tail - file_base` cannot support the durable frontier; valid retained records should already have extended it. The selected narrow recovery defense refuses that state before barrier, publication, appender advancement or sidecar strengthening. Compacted prefixes and inherited fork bytes lie below `file_base`, stale proofs below that base remain skipped, and legacy sidecars without proof still begin from physical size.

The old recovery assertion catches a first-record hole only in debug builds, after its positioned write has already materialized a gap. A bad boot can propagate this issue into a retained WAL record beyond physical EOF. The selected production defense tracks actual contiguous logical EOF per replay-touched stream, seeded once from live-file metadata rather than durable proof. It refuses every in-range record whose start exceeds that end before writing, permits overlap/adjacency, and advances the tracked end only after successful writes. It checks both first and later holes without a filesystem stat per record. Synthetic old-proof/gap fixtures must demonstrate their own semantic failures before those defenses land; they are separate qualification, not additional claims of a real checkpoint-race reproduction.

On such a refusal the WAL must remain unreset and the offending gap record must not alter the failing file. Earlier legitimate replay writes and healthy shards may already have repaired other data; this is not a global two-phase recovery or store-wide artifact-preservation guarantee. A same-length sparse/zero-filled hole already materialized by an older release cannot be detected solely from lengths; independent content proof and repair remain outside this boundary. The guards must also qualify successful repair of shortened files by retained WAL and existing fork/compaction recovery.

## Implemented resolution and executed qualification

The capture boundary is installed in both stream constructors and both body-write paths. The checkpoint worker takes only that short boundary and the shared-state read lock to clone the tail/file pair. The recovery EOF map replaces the prior replayed-stream set and debug-only maps; its entries retain the same unconditional repair-fsync behavior without another per-stream collection. Physical EOF and record-end arithmetic are checked. A replay error aborts further application in that shard; startup joins recovery workers and returns before WAL reset, committer startup or serving.

Three deliberately synthetic corruption defenses were executed red before recovery changes (`bun run test:durable-streams e2e_recovery_refuses_ -- --nocapture`, exit 101):

- A false checkpoint tail of 521 after actual baseline WAL recycling booted successfully three times over nine physical bytes.
- A first retained record at 521 created a 526-byte zero-filled gap before the debug assertion panicked; the next boot accepted the materialized gap and reset the WAL.
- A later retained record at 521, following a legitimate record at zero, escaped the debug minimum-offset assertion and booted at 526.

These are old-corruption defense fixtures using real WAL encoding and recovery, not three additional HTTP race reproductions. With the guards, all three return named `InvalidData` errors on three consecutive boot attempts while preserving the failing stream's data/metadata, its proof where applicable, and retained WAL. The positive short-file fixture retains valid WAL, repairs an overlapping prefix followed by two contiguous extensions, and preserves exact bytes and all frontiers across two boots.

Eight new regressions cover the real rejected POST, rejected initial PUT, WAL durability before reader publication, one-blocking-worker progress, the three synthetic defenses and retained-WAL repair. The reader-lag fixture actually rolls and recycles the paused append's WAL segment, records its six-byte accepted prefix while the reader frontier remains zero, then publishes the later append first and verifies exact thirteen-byte state across two boots. Both rejection fixtures acknowledge another stream on the same shard while target capture waits. The one-worker fixture holds the real async appender while queued metadata IO must progress; it models compaction's resource ordering rather than executing a full `compact_one` overlap. The earlier 0029 fixture separately qualifies a captured prefix followed by a later rejected append.

The handler pauses and full process restarts exercise actual staging, checkpoint and recovery paths, but they are not power-loss experiments. Existing compaction, deletion, fork and crash-simulation coverage provides compatibility qualification, not proof of every possible overlap. No automatic corruption repair, content checksum or benchmark was added.

Coordinator inspection and independent review found no blocking issues.
