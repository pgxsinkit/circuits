# 0029 — General metadata writers can capture speculative append state

Status: resolved (fixed 2026-10-03)
Opened: 2026-10-03 · Area: `apps/durable-streams/src/store.rs` metadata sweep/capture, `wal/shard.rs` checkpoint, `handlers.rs` append
Reopen trigger: regression in committed metadata capture, close ownership/retry or cancelled staged-request completion; checkpoint tail-proof and notification ordering have separate entries 0030/0031.

Urgency: resolved medium durability defect for ordinary log-server writes. No production incident is known. This route did not require DS forks.

## Original source evidence and scope

The review of [0018](0018-fork-refcounts-persist-speculative-parent-metadata.md) found an independent writer route. `handle_append_inner` changes `closed`, `closed_by`, producer state and `last_seq_header` before staging the WAL record. Stage failure restores the live state and truncates the attempted data bytes. `Meta::capture` reads those same shared fields. Its `meta_lock` serializes metadata writers and excludes hard deletion, but append mutations do not acquire it.

`Store::sweep_meta_once` checks the registry incarnation and dirty flag, then writes the general snapshot. An earlier memory-mode append or TTL read can already have queued that stream. WAL `checkpoint_blocking` drains dirty streams and may flush an earlier `meta_dirty` flag without acquiring the appender or draining admitted append operations. A previously completed producer/sequence/TTL append can therefore supply the dirty work while a later append has speculative state in memory. Sealing/offload writers in `tier.rs` also write general snapshots while later appends can run: their operation admission excludes deletion, not other admitted appends. Compaction holds the appender mutex, making its pre-stage overlap narrower. These are source observations, not a demonstrated crash image; qualify each writer before claiming complete coverage.

The documented lag in persisting a completed producer/access update is a separate contract: this candidate concerns persistence ahead of staging, including metadata from a rejected append. Narrow reference-only writes fix the fork-induced route in 0018; they do not establish a committed snapshot for general writers. Fork graph recovery remains [0019](0019-fork-graph-and-reference-recovery.md).

## Original reproduction plan and acceptance

Use the existing WAL stage hook and a deliberately oversized record to pause a real close/producer/sequence POST after shared-state mutation, then force a staging failure after the hook. First arrange dirty work with an earlier successful write or TTL read. Cross the pause with the real metadata sweep or checkpoint, inspect the sidecar, release the append, assert HTTP 500 and live rollback, then crash/reopen. Keep all background owners quiescent before reopening the directory; compare committed bytes and every affected metadata field. Demonstrate the failure before choosing a fix, and test sweep and checkpoint separately.

The sweep fixture plan uses the WAL harness with 256-byte segments and a TTL-60 stream. Commit producer epoch 1/sequence 0 with `Stream-Seq: 0000`, checkpoint the baseline and clear its dirty flag, then call `get_for_read` to queue a legitimate renewal. Pause a 512-byte POST carrying producer sequence 1, `Stream-Seq: 0001` and close. Call `sweep_meta_once` from a blocking worker, retain the parsed sidecar in test memory, then always release the hook and join the append before assertions or runtime teardown. Assert HTTP 500, live rollback, and reopen preserving the baseline producer/sequence/open state and bytes. This plan was subsequently implemented and executed as recorded below.

Choose an explicit committed-state or writer-admission boundary. Do not solve it by blocking the metadata writer on an appender which itself waits for that writer, or by dropping dirty work on contention. Preserve close visibility, producer retry behavior, writer sequencing, TTL lag, tier manifest/compaction atomicity and lifecycle cancellation. Include failed staging and storage writes, concurrent successful appends, delete exclusion, and crash/reopen. Run both repository gates after implementation.

## Executed reproduction and selected boundary

`bun run test:durable-streams e2e_general_meta -- --nocapture` exited 101 with both intended regressions red. The real-handler fixtures in `wal/e2e_tests.rs` first commit and checkpoint producer sequence 0 / writer sequence `0000`. The sweep case queues a legitimate TTL GET renewal and crosses a rejected sequence-1 close append; the checkpoint case commits sequence 1, pauses its checkpoint after tail capture/barrier, and crosses a rejected sequence-2 close append. The existing checkpoint hook gained a test-only setter. Both fixtures verify POST 500, live metadata rollback and exact acknowledged bytes before and after full recovery before comparing metadata. The saved sidecar, recovered sidecar and reopened state all contain the failed sequence and closure. Sweep's acknowledged tail remains 9 bytes; checkpoint's remains 15. The earlier proposed sweep command is now implemented and executed as part of the two-case filter.

Checkpoint's pause deliberately isolates metadata contamination from speculative tail-map capture. That separate source lead is [0030](0030-checkpoint-tail-can-cross-a-rejected-append.md); it has not been executed locally.

The selected implementation uses one producer map with writer and committed values per entry, plus a committed writer-sequence value. General metadata capture reads only committed producer/sequence values and reader-visible closure. Successful ordinary appends promote their request-owned deltas after durability, monotonically despite out-of-order callbacks. Insertion and stage rollback preserve an earlier callback's committed promotion. This avoids a second key/map allocation per producer and avoids acquiring the appender from metadata writers; compaction already holds the appender while awaiting its metadata write.

Close gets a dedicated writer behind `meta_lock`: overlay the validated close candidate on committed metadata, persist it, then promote closure and notify readers inside the owned blocking task before releasing the writer barrier. A later general capture cannot reopen a successfully committed close. Matching pending close retries must retry or refuse temporarily, rather than acknowledge writer intent alone. Pending producer duplicates likewise require committed sequence proof before a successful reply.

Before production edits, `bun run test:durable-streams e2e_duplicate_does_not -- --nocapture` produced three additional intended semantic failures. With committers stopped and a real append waiting for its WAL barrier, ordinary and close duplicates returned 204 rather than retryable 503. A retry of committed sequence 0 while sequence 1 was pending reported `Producer-Seq: 1` rather than committed 0. Each fixture restarted the committer, joined the original successful POST and fully reopened before its final assertion. The initial fixture header-accessor compile mismatch was corrected before this run and is not counted as red evidence.

A directory-fsync failure after rename is uncertain: a HTTP-500 close may recover closed if the candidate rename survives. Do not promise every failed close recovers open. The guarantees are no pre-stage speculative metadata, no successful durability reply/reader EOF before confirmed close durability, and no reopening by stale general writers after a successful close. TTL access policy, fork graph recovery (0019), and durable create compensation (0025) retain their separate boundaries. Independent review also found the preexisting tail-watch publication lead [0031](0031-tail-watch-publication-can-regress-after-close.md), which concerns notification ordering rather than the metadata snapshot.

## Qualification and limits

The original five semantic regressions now pass. Seven follow-on tests were added after the fix: close-only refusal behind pending bytes; replacement/directory-sync close failures with matching and mismatched retries; reordered same-epoch and new-epoch callbacks; earlier committed promotion surviving a later stage rollback; cancelled close with a subsequent metadata writer; cancelled close with real DELETE draining; and memory-mode/initial-body/create-closed PUT recovery. The failure/retry fixture checks original ownership and writer sequence across concurrent producer-owned and empty producerless retries without appending their bodies twice. It does not force the producerless retry to be the first committing worker. Only the original five have demonstrated red-to-green evidence.

The first cancellation fixtures abort a direct handler after the blocking close worker has started and fsynced its candidate, before publication. They prove retained operation admission, deletion exclusion and detached publication. The raw HTTP listener awaits its handler before attempting response socket writes, with no disconnect cancellation selection in that path; these are not executed socket-disconnect experiments.

The full validation gate then found a separate completion gap in the existing crash simulation: seed 89837, generation 1 refused close with 503 after an ordinary handler was cancelled mid-flight. A deterministic real-handler fixture stopped the committer, staged a producer/sequence body append, aborted its caller, then resumed durability. It observed operation admission 0, no eventual publication, and duplicate/close responses 503, while full recovery restored the exact body bytes. The equivalent initial PUT fixture also failed semantically: admission 0, no publication, matching create retry 200 but later close 503; full recovery restored its exact five body bytes. These distinguish abandoned post-WAL completion from a merely delayed committer or metadata corruption.

The extension installs completion ownership immediately after successful staging and before its first await. Ordinary completion remains inline; dropping a pending guard spawns an owned continuation with its request metadata and original operation admission. Initial PUT's body uses the same stage/wait/publication seam and retains admission through response construction without changing its tier scheduling. Close transfers ownership synchronously into its blocking worker before awaiting it, so an intentional storage error does not trigger accidental background retries. A detached continuation does not recursively reschedule itself if runtime teardown cancels it; WAL recovery then owns completion. Cancellation before create completion and the full shutdown bound remain separate (0025/0026).

Both new semantic failures went green. Two more tests qualify a body-close cancelled during its WAL wait and a close issued immediately after cancellation while the committer remains stopped: the latter must return 503 with reader tail zero/open, then publication and a matching close retry must complete after durability. The existing simulation now retries only 503 inside a timeout around the entire two-second close loop, fails on timeout/other errors, and additionally requires actual durable EOF before accepting a successful response. Its abort comments describe direct handlers rather than claiming a socket-disconnect model. Seeds 89837–89840 pass. Across the batch, seven of the sixteen new tests have executed red-to-green evidence; nine were added after the relevant fix.

Sweep and checkpoint each have an executed paused failed-append/reopen fixture. Tier sealing, offload and compaction call the same corrected capture function; their existing suites check compatibility and lock progress, but no separate paused failed-append tier fixture was added. Power loss during rename/directory fsync was not simulated. The persisted producer/access lag contract is unchanged, and the extra committed producer values do not establish a cardinality or RSS ceiling. Checkpoint's writer-tail capture (0030) and notification ordering (0031) are source-only leads, not results of these regression tests.

## Final validation

Bounded implementation and independent review found no remaining findings. Focused tests passed: all 45 WAL end-to-end cases, 45 store cases including concurrent append/seal/compaction, six tier helpers and the default four-seed crash simulation. The first gate caught three APIs newer than the crate's declared Rust 1.75 minimum; equivalent `map_or` expressions resolved them without changing the toolchain or dependencies. The subsequent simulation failure led to the additional cancellation reproductions and repair above, rather than accepting permanent 503.

Both `bun run validate` and `bun run validate:full` passed on the final source: 425 engine Rust unit tests and its other binaries, 193 log-server unit tests, eight log-server CLI cases, 82 TS unit tests, 246 engine integration cases across 61 files and 332 protocol cases. Existing two Rust ignores and six protocol skips remain. PostgreSQL 18 binaries were on PATH; command output was captured directly, with no redirected logs. No dependencies or branches changed. Architecture docs and the resolution ledger describe the final ownership/capture boundary and its exclusions.
